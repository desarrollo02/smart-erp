# Sprints

Cada Sprint tendrá una carpeta propia con objetivo, historias, secuencia de ejecución, resultados, demostración y retrospectiva.

La demostración es un gate obligatorio de cierre. Debe ser visual, navegable y
ejecutarse sobre el baseline real mediante un guion reproducible. Incluso un Sprint
técnico debe mostrar su incremento desde una vista segura del producto; una demo no
autoriza inventar funcionalidad ni sustituye pruebas, seguridad, evidencia o PDF.
Cada cierre conserva resultados en 375, 720 y 1280 px y declara capacidades y
límites sin ambigüedad.

Los documentos deben registrar las pruebas realizadas después de cada cambio coherente y no pueden declarar completada una historia con validaciones pendientes o fallidas.

La candidata visual de Sprint 3 tiene una excepción temporal de calendario aprobada el 2026-07-28: las pruebas automatizadas se acumulan en su historia de cierre. El trabajo previo usa el estado `Implementada pendiente de validación`, por lo que la regla de no declarar historias completadas continúa intacta.

El responsable de producto aclaró el 2026-08-11 que la continuidad funcional
posterior a Sprint 8 difiere únicamente la validación independiente asignada a
otra persona. Todas las pruebas automatizadas aplicables siguen siendo
obligatorias en cada corte. Los Sprints permanecen abiertos y no promocionables
hasta completar además composición, gates runtime y aceptación independiente.
